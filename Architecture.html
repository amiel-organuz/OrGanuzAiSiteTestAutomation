Playwright automation with Product E2E Matrix, QA orchestration, FastAPI, Scalar, Grafana, Prometheus, Organuz Supabase API tests, and Allure 3

A single-file architecture view for the OrGanuz AI site automation stack. Local runs start the runtime services, execute the six Playwright projects, generate Allure 3, and print the main service links. The product project carries the property-characterization matrix and role data-contracts plus the dev UI-token sanity spec; product-setup → product-authenticated add live per-role browser sessions; chromium covers the marketing site, organuz-api the Supabase/PostgREST backend, and agent the QA-orchestrator regression plus the TestPlanAgent (URL → Playwright-MCP exploration → generated test plan). GitHub Actions runs the same projects in parallel and publishes Allure to GitHub Pages.

Stack Overview

TS Playwright Tests

Six projects: chromium (marketing UI), product (token-sanity + matrix & role data-contracts), product-setup → product-authenticated (live per-role sessions), organuz-api (Supabase/PostgREST), and agent (orchestrator regression + TestPlanAgent URL→plan generator). 59 tests: 46 green (chromium 12, product 31, organuz-api 1, agent 2) + 13 credential-gated role specs that skip until per-role secrets exist.

E2E Product Coverage

tests/product runs the dev UI-token sanity spec (3 checks, skipped only on a dev-gateway outage) and the matrix data-contract (13 checks over 12 CALC-ROOF scenarios × 4 personas, property/polygon/roof coverage, panel thresholds, Ramot, and the UI-only no-panel case).

PY FastAPI

Provides /health, /metrics, /openapi.json, built-in docs at /docs, and automation metadata under /automation.

API Organuz Backend

The organuz-api project tests the Organuz Supabase/PostgREST backend — the /rest/v1/projects resource and edge-function CORS preflights — using the public anon key.

RPC Dev RPC token

The product token-sanity spec opens the dev calculator, captures the UI token off the wire, and calls the dev RPC gateway at organuz.flamiingo.com (POST /?call=<method>) — proving the bundled public token authorizes the gateway and is sent in the request body over HTTPS, never in the URL.

DOC Scalar API Reference

External Scalar docs read the FastAPI OpenAPI schema from localhost:8000/openapi.json.

MON Pushgateway

The Prometheus Pushgateway (prom/pushgateway, host 9091) receives the qa_playwright_* test metrics that scripts/push-qa-metrics.mjs pushes after each run; Prometheus then scrapes it with honor_labels: true.

MON Prometheus

Scrapes FastAPI process metrics from api:8000/metrics and the QA test metrics from the pushgateway, both through server/prometheus.yml.

MON Grafana

Runs on host port 3001 with a provisioned Prometheus datasource and the OrGanuz QA Dashboard.

REP Allure 3

Generated by the CLI and CI workflow, served locally by Nginx, and published by GitHub Pages on main branches.

FAIL Failure Capture

src/fixtures/index.ts attaches screenshots, videos, and traces to Allure after unexpected failures; Playwright is configured with screenshot: only-on-failure, video: retain-on-failure, and trace: on-first-retry.

AGENT QA Orchestrator

Coordinates Azure DevOps, Google Sheets, Playwright, and OneDrive. The CLI-backed runner maps orchestrator cases to real Playwright projects and reports pass/fail evidence back through the agent loop. Its sibling TestPlanAgent goes the other way — given a URL, it drives the Playwright MCP CLI server (npx @playwright/mcp) to explore the live page and generate a TestSuite (npm run agent:plan -- <url> --live).

Architecture Diagram

QA Agent Orchestrator Stack

The QA Agent Orchestrator coordinates multiple testing tools and integrations to automate the verification pipeline:

Azure DevOps

System of record. The orchestrator reads test plans, writes back outcomes, and files bugs idempotently (guards against duplicates).

Google Sheets

Provides parameterized input/expected values and environment configurations, and logs live results.

Playwright Runner

CliPlaywrightRunner invokes npx playwright test for mapped projects, reads test-results/results.json, and returns normalized execution results to the orchestrator.

OneDrive Store

Durable evidence storage. Returns shareable links that are linked in reported DevOps bugs.

Current Test Mapping

npm run agent:current-tests maps PW-API, PW-CHROMIUM, PW-PRODUCT, and PW-AGENT to the real Playwright organuz-api, chromium, product, and agent projects (each case runs a whole project).

Agent Current-Test Flow

1

Build agent

npm run agent:current-tests first compiles TypeScript with tsc -p tsconfig.json.

2

Create suite

run-current-tests.ts creates stubbed ADO/Sheets/OneDrive connectors and a generated suite for the repository's Playwright projects.

3

Run projects

CliPlaywrightRunner executes --project=organuz-api, --project=chromium, --project=product, and --project=agent as orchestrator cases.

4

Report outcome

The orchestrator uploads report artifacts, writes case results, files bugs for failures, logs Sheets rows, and returns a JSON run summary.

CLI Flow

1

Typecheck

npx tsc --noEmit validates the TypeScript framework before tests run.

2

Start stack

The script starts FastAPI, Scalar, Prometheus, the Pushgateway, and Grafana when local endpoints are not ready.

3

Run tests

npm test executes all four green projects — chromium, product, organuz-api, and agent — in one run. The local shell flow runs them while the service containers are online, then scripts/push-qa-metrics.mjs pushes the run's qa_playwright_* metrics to the Pushgateway so Grafana shows fresh results.

4

Serve reports

Allure 3 is generated and served through the local Nginx allure service.

Product Matrix Data Contract

The matrix is checked-in test data, split across tests/product/matrix/ — matrix-types.ts, matrix-constants.ts, product-personas.data.ts, and property-scenarios.data.ts, re-exported through the e2e-matrix.data.ts barrel. product-matrix-data-contract.spec.ts asserts the shape of that data (no browser, no network); it encodes the working E2E matrix document so drift is caught in CI.

  • 12 main CALC-ROOF-001 to CALC-ROOF-012 characterization scenarios.
  • 4 personas per main scenario: customer, consultant, company, and company employee.
  • Property types: private house, residential building, commercial, agricultural, and public.
  • Polygon behavior: building, parking, sports court, and mixed building + parking/sports-court flows.
  • Roof and surface types: concrete, tiles, iscoverit, parking, and sports court.
  • Negative coverage below the QUOTABLE_MINIMUM_PANEL_COUNT threshold and UI-only tracking for the no-panel case.
  • Invariants checked: unique scenario ids, arena/panel-mode consistency, empty roof-payload placeholders, and a pinned scenario × persona count.

Test Suites — Every Group in Detail

Six Playwright projects, run identically locally and on GitHub Actions. 59 tests total: 46 green + 13 credential-gated role specs that skip until per-role secrets are added (see the test-suite-parity skill). A seventh monitoring project is opt-in (registered only when MONITORING_ENABLED=true) and adds 50 live third-party availability checks (109 total); it runs under the External API Monitoring workflow, never in the default green gate. Counts below are per spec file.

UI · 12 chromium  tests/ui/** · @other-smoke · prod www.organuz.ai

Visibility-only sanity checks against the live marketing site. No form submissions, so nothing reaches the real CRM; each spec calls homePage.navigate() which waits for the hero to render before asserting.

  • homepage/hero.spec.ts (1) — the H1 hero heading is visible and contains “אור”.
  • homepage/navigation.spec.ts (1) — the header CTA (“להתחלה”) is visible and its href points at the app (energy.organuz.com).
  • homepage/sections.spec.ts (5) — the six primary nav links are visible; the hero subtitle is visible; all six audience/user-type buttons are visible; the “Why Organuz” heading + first audience tab; the “Meet Or” heading + its “talk to Or” CTA.
  • content/homepage-content.spec.ts (3) — all six named AI agents are shown; the active-projects showcase heading is visible; the FAQ heading + the first known question are visible.
  • homepage/contact.spec.ts (1) — the contact form exposes name, email, phone, message, and submit (presence only).
  • content/blog.spec.ts (1) — /blog loads with the page heading and at least one article card.

E2E · 31 product  tests/product/** (ignores flows/**) · no grep · dev (QA_TARGET_ENV)

  • api/token-sanity.spec.ts (3, live) — opens the dev calculator, captures the UI token off the wire, and hits the dev RPC gateway. Checks: (1) the token is well-formed (24-hex-id-32-hex-secret); (2) it matches the bundled public token in config.devApi.token (bundle/config-drift guard); (3) every captured backend call is HTTPS, sends the token in the body (never the URL), and targets only the gateway host. Skips when the dev gateway is down (no token extractable).
  • api/public-app-sanity.spec.ts (5, live) — public (no-login) checks after unlocking the password gate: the calculator shell renders; a fresh visitor is signed out; the header sign-in/register entry point is visible; the app is served over HTTPS on the configured dev host; and the app fires at least one token-bearing backend call on load. Skips on a genuine dev outage (AppUnavailable), fails only on a real product regression.
  • matrix/product-matrix-data-contract.spec.ts (13, offline) — asserts the shape of the checked-in matrix data: runtime-only fields excluded from committed fixtures; the scenario × persona matrix size is a pinned 48; the 12 CALC-ROOF ids; full property-type / polygon / roof-surface coverage; roof-payload placeholders are empty {}; the no-panel scenario is UI-only; scenario ids are unique; arena type matches each group; the negative scenario sits below QUOTABLE_MINIMUM_PANEL_COUNT; only the company persona has elevated rights; panel counts align with each panel mode.
  • matrix/product-roles-contract.spec.ts (10, offline) — role-capability data contract for the three sign-in roles: all three are modeled and distinct; each has a name + role description; a valid post-funding destination; customer is the only role routed to quotations; customer/consultant can open quotations from results while company downloads its own; only company can open company pricing / management; company is the sole holder of elevated rights.

SET · 3 product-setup  support/auth.setup.ts · dependency of product-authenticated

Authenticates each sign-in role (customer, consultant, company) once via phone + fixed dev OTP and saves storageState to playwright/.auth/product-<role>.json (gitignored). One skip-safe test per role: a role with no <ROLE>_PHONE credential — or when the dev app/OTP is unavailable — is skipped, and no session file is written.

AUTH · 10 product-authenticated  tests/product/flows/** · depends on product-setup

Live per-role browser e2e that resumeSession() from the saved storageState and run read-only checks (no logout/writes, so a shared session is never invalidated). Each test skips when its role has no saved session — so the whole project is green without per-role credentials. Per role (customer, consultant, company):

  • Resumes the saved session into an authenticated calculator shell.
  • Opens the role’s personal area.
  • The session persists across a page reload.
  • Company only: opens the contractor pricing area (מחירון) from its personal area.

API · 1 organuz-api  contracts/ · @other-smoke

One live contract test against the Supabase/PostgREST /rest/v1/projects resource (public anon key). Over every returned row it asserts: 200 + JSON non-empty array; all required fields present and non-null; numeric and string-array field types; and each bilingual (he/en) pair present and non-empty.

QA · 2 agent  orchestrator/ · test-plan/ · @other-smoke

Two unit specs (pure stubs, no network/browser): (1) an orchestrator regression — a runner crash is marked blocked and the suite keeps running, proving crash isolation through the real Orchestrator with stubbed Azure DevOps / Sheets / OneDrive / Playwright connectors; (2) a TestPlanAgent spec — a URL is explored through a fake Playwright-MCP client and a TestSuite (page-load, headings, per-link, form cases) is generated, incl. parsing the real MCP aria snapshot.

MON · 50 monitoring  tests/monitoring/** · opt-in (MONITORING_ENABLED=true) · live third-party

Dedicated availability + contract monitoring for the two critical third-party map dependencies the product relies on, using APIRequestContext only (no browser). This project is registered only when MONITORING_ENABLED=true, so it never runs in the default 59-test suite (109 with it); it is driven separately by the External API Monitoring workflow (monitoring.yml, cron every 30 min) and is meant to fail when a dependency is down — that failure is the alert (auto-managed GitHub issue + Slack), so a Govmap/Ofek outage can never break the green PR gate.

  • govmap.spec.ts (25, live) — Govmap (www.govmap.gov.il): the map API and address geocoding.
  • ofek.spec.ts (25, live) — Ofek (basemaps.govmap.gov.il): the Survey-of-Israel national orthophoto tiles the roof scan runs on.

Per-Role Session Architecture

The dev app rate-limits OTP per phone, so each role logs in once per run (in product-setup) and every per-role spec reuses that session. Missing credentials or a saved session skip cleanly, so the suite is green without secrets.

  • auth.setup.ts logs each role in (phone + fixed dev OTP) and saves storageState to playwright/.auth/product-<role>.json (gitignored); auth.ts maps a role to that file.
  • Per-role specs set test.use({ authRole }); the product fixture loads the saved storageState, and product.resumeSession() restores the session without a new login.
  • ProductAppPage.ts drives login, the password gate, the characterization wizard, and personal-area navigation; ProductFlows / RegistrationFlows compose them into journeys; TokenInterceptor captures the UI token.
  • Three roles sign in: customer, consultant, company. company-employee is modeled in the matrix but has no phone and cannot sign in.

Typed Environmental Errors

Outages are modeled as typed, instanceof-safe errors in tests/product/support/errors.ts so the page object and flows stay free of test-lifecycle decisions.

  • OtpUnavailableError / AppUnavailableError extend a base that restores the prototype and name (Playwright's transpiler otherwise severs extends Error).
  • ProductAppPage, env-gate, and ProductFlows throw these; the test edge decides whether to skip or fail.
  • In practice the one sanctioned skip is token-sanity: when the dev gateway is down and no token can be extracted, beforeEach skips rather than failing the product job.
  • A token that is observed but malformed/drifted still fails as a real regression.

Tags & Gating

  • @other-smoke — the default filter for the non-product projects; every chromium (12), organuz-api (1), and agent (2) test carries it.
  • @ui — marketing-site specs; @organuz-api @contract — the backend contract test.
  • @product @api @sanity — the dev token-sanity spec (@critical/@security on individual checks); @product @roles @e2e — the live per-role specs. The product project has no grep filter, so every matched spec runs.
  • Sanctioned env-conditional skips: token-sanity (dev-gateway outage) and the live role specs (product-setup + product-authenticated, no credential/session). Everything else must pass — baseline 40 passed, 13 skipped.
  • Specs run fully parallel (fullyParallel: true); data-contract and stubbed-agent tests share no state, and role specs reuse read-only saved sessions.

QA Dashboard Metrics

scripts/push-qa-metrics.mjs reads the latest Playwright JSON report (test-results/results.json, override QA_PLAYWRIGHT_RESULTS_PATH) and pushes the metrics to the Prometheus Pushgateway (PUSHGATEWAY_URL, default http://localhost:9091); Prometheus scrapes the Pushgateway with honor_labels: true and Grafana provisions the QA dashboard automatically. FastAPI's /metrics now serves only its own process_* / up metrics — it no longer reads the results file, which retired the old stale-bind-mount refresh hack.

  • qa_playwright_tests_total{project,status} for pass/fail/skipped counts.
  • qa_playwright_duration_seconds{project} for project runtime.
  • qa_playwright_last_run_timestamp_seconds for report freshness.
  • qa_playwright_report_present for “latest report loaded” status.

Backend API and Failure Capture

Organuz Supabase API

  • The organuz-api project (tests/organuz-api/contracts/) targets the Organuz Supabase/PostgREST backend.
  • Base URL and public anon key come from config.json → organuzApi (env override ORGANUZ_API_ANON_KEY).
  • The live contract test asserts the /rest/v1/projects schema: every required field present and non-null, numeric/array field types, and each bilingual (he/en) pair present and non-empty.
  • The OrganuzApi client (read-only) plus RestApiConstants centralize the REST paths, PostgREST filters, and Prefer headers; the anon role is intentionally not permitted to write.
  • The dev product-app RPC gateway (organuz.flamiingo.com) is exercised indirectly by the product token-sanity spec, not by a separate project.

Failure Artifacts

  • src/fixtures/index.ts attaches screenshots, videos, and traces to Allure after unexpected failures.
  • Playwright is configured for screenshot: only-on-failure, video: retain-on-failure, and trace: on-first-retry.
  • The agent orchestrator spec deliberately simulates a runner crash (marked blocked) to prove crash isolation — it passes; it is not an expected-failure demo.
  • Backend/API logging is inverted through an onExchange callback the fixture points at Allure, so the API client has no test-framework dependency.

GitHub Actions

  • typecheck validates TypeScript.
  • tests runs chromium, organuz-api, agent, product, and product-authenticated as a fail-fast: false matrix, identical to the local default run (product-setup runs as product-authenticated's dependency). Keep in sync per the test-suite-parity skill.
  • The product shard sets QA_TARGET_ENV: dev and needs the PRODUCT_PLATFORM_PASSWORD secret (token-sanity opens the dev calculator); a missing secret shows as 3 skips, not a red job.
  • Chromium is installed only for the chromium and product shards; organuz-api and agent need no browser.
  • services-smoke starts FastAPI, Scalar, Prometheus, and Grafana.
  • publish-allure merges Allure artifacts and generates Allure 3.
  • deploy-allure publishes the report to GitHub Pages on main or master.
  • report-summary writes Allure, FastAPI, Scalar, and Grafana links into the Actions summary.
